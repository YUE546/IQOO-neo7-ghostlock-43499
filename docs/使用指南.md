# iQOO Neo7 Root 使用指南（GhostLock-MT6983T）

> 适用设备：iQOO Neo7（V2231A/PD2231，天玑 9000+/MT6983T，OriginOS Android 15，
> 内核 5.10.233-android12-9）
> 原理：GhostLock（CVE-2026-43499）内核提权 → SakiSU 内核模块接管 root
> **每次开机后需重新执行**（BL 官方不可解，root 不持久化）

---

## 一、文件清单（仓库内）

| 文件 | 说明 |
|---|---|
| `exploit/bin/gl_mcast43` | exploit（r43 定版，需推送到手机） |
| `ksu/sakisu_raw.ko` | SakiSU 内核模块（未补丁，补丁链输入） |
| `ksu/patch_vermagic.py` | 补丁 1：vermagic 重写（vivo 门禁） |
| `ksu/patch_shnabs.py` | 补丁 2：未导出符号地址注入 |
| `ksu/unknown_syms.txt` | 50 个未导出符号列表 |
| `ksu/ksu_loader.sh` | 两阶段 KSU 加载器（设备端执行） |
| `ksu/SakiSU.apk` | SakiSU 管理器（包名 com.sakisu.sakisu，手机端安装） |
| `scripts/onekey_root.bat/.ps1` | 一键自动化（推荐） |
| `scripts/fix_ashmem.sh` | ashmem 节点兜底修复（boot_id 已内核侧恢复，通常无需） |

## 二、电脑端准备

1. **adb**：下载 Android SDK Platform Tools，解压到任意目录（如
   `D:\Android\platform-tools`），记下 `adb.exe` 完整路径。
2. **Python 3**：安装时勾选「Add Python to PATH」，命令行验证
   `python --version`。
3. **USB 驱动**：能 `adb devices` 看到设备即可。

## 三、手机端一次性配置（首次使用前）

1. **开发者选项**：设置 → 系统管理 → 关于手机 → 连点「软件版本号」7 次 →
   返回进入开发者选项。
2. **开发者选项内开启**：
   - ✅ USB 调试（必须）
   - ✅ 停止限制子进程 / 停用 adb 超时（必须，否则 exploit 进程会被系统杀死）
   - ✅ USB 安装（可选）
3. **安装 SakiSU 管理器**：安装 `ksu/SakiSU.apk`，打开一次完成初始化。
   **无需提前开启 adb root**——KSU 模块加载后再授权。
4. **推送 exploit**（首次需要；exploit 更新后一键脚本也会自动校验哈希并重推）：

```bat
adb push exploit\bin\gl_mcast43 /data/local/tmp/gl_mcast43
adb shell "chmod 755 /data/local/tmp/gl_mcast43; mkdir -p /data/local/tmp/rundir /data/local/tmp/p5"
```

## 四、每次开机后的 Root 流程

### 方式 A：一键脚本（推荐）

1. 修改 `scripts/onekey_root.bat` 里的 `ADB` 路径（若 adb 不在 PATH）。
2. 手机重启到干净状态 → USB 连接 → 双击 `scripts\onekey_root.bat`。
3. 脚本会自动完成：状态检查（脏 boot 自动重启）→ 发枪（失败自动重试，最多
   3 次，期间实时显示 exploit 日志）→ 拉 kallsyms → 本地补丁 → insmod →
   ashmem/网络修复 → 验证。
4. **中途需要手机操作一次**：脚本会自动打开 SakiSU 管理器，在手机上于弹出的
   授权请求点【允许】即可（电脑端自动轮询等待，无需回车确认）。

### 方式 B：手动分步

> 以下 `adb` 指你的 adb.exe 完整路径或加入 PATH 后的命令。

**Step 0 确认干净状态**

```
adb shell cat /proc/sys/kernel/random/boot_id
adb shell cat /sys/fs/selinux/enforce
adb shell ls /sys/module/kernelsu
```

三个判据：boot_id 为正常随机 UUID、enforce 为 `1`、**kernelsu 模块不存在**
（`ls` 报 No such file）。注意 bootid 内核侧恢复后，成功提权过的 boot 的
boot_id 也会读回原始 UUID、enforce 也可能是 1 —— **必须查 KSU 模块残留**，
存在说明本轮已提过权，`adb reboot` 后重来。若 boot_id 为 `72303030-...`
样式或 enforce=0，同样重启后重来。

**Step 1 推送两阶段加载器**

```
adb push ksu\ksu_loader.sh /data/local/tmp/rundir/ksu_loader.sh
adb shell "chmod 755 /data/local/tmp/rundir/ksu_loader.sh; rm -f /data/local/tmp/ksu_ready /data/local/tmp/ksu_stage1.log /data/local/tmp/ksu_stage2.log /data/local/tmp/kallsyms.txt"
```

**Step 2 发枪**

```
adb shell "cd /data/local/tmp && KSU_RUNDIR=/data/local/tmp/rundir KSU_LOADER=1 FLIP_PERMISSIVE=1 SYSCTL_WALK_ATTEMPTS=4 SLIDE_MCAST_SHIFT=21 SLIDE_MCAST_GAP_US=300 SLIDE_MCAST_ROUNDS=10000 GL_ANCHOR_SURVIVE=1 nohup ./gl_mcast43 > run.log 2>&1 &"
```

等 30–60 秒再检查（**发枪窗口期内不要跑其他 adb 命令**——exploit 的栈时序对调度
噪声极敏感，轮询会干扰甚至直接打死它）：

```
adb shell "grep -c 'exploit chain complete' /data/local/tmp/run.log"
```

输出 `1` 即成功。实测成功率 90% 以上；失败一般是链路自行中止（设备还活着、
boot_id 可能写脏）或偶发卡死重启，重启后重跑即可。

**Step 3 拉 kallsyms**

```
adb shell cat /data/local/tmp/ksu_stage1.log        REM 应显示 KALLSYMS_DONE size=...
adb pull /data/local/tmp/kallsyms.txt ksu\kallsyms.txt
```

**Step 4 本地补丁**

```
cd ksu
python patch_vermagic.py sakisu_raw.ko ksu_v.ko
python patch_shnabs.py ksu_v.ko ksu_final.ko unknown_syms.txt kallsyms.txt
```

第二条会输出 `patched 49 != resolved 50` 警告——**正常**，不影响使用。
生成 `ksu_final.ko`（约 367KB）。

**Step 5 加载模块**

```
adb push ksu_final.ko /data/local/tmp/p5/ksu_final.ko
adb shell touch /data/local/tmp/ksu_ready
adb shell "sleep 5; cat /data/local/tmp/ksu_stage2.log"
adb shell lsmod | findstr kernelsu
```

应看到 `INSMOD_DONE rc=0` 与 `kernelsu 208896 0`。

**Step 6 授权 SakiSU + adb root（关键）**

1. 打开 SakiSU 管理器，弹出授权请求点【允许】（一键脚本会自动帮你打开管理器）
2. 进「超级访问/设置」，开启【ADB root】（开过不生效就关了再开）
3. 电脑端：`adb root`，等 5 秒，`adb shell id` 应显示
   `uid=0(root) context=u:r:ksu:s0`

> **实测**：授权不跨 boot 自动生效，每次 insmod 后都要在手机上点一次允许。
> **重要**：不要通过 exploit 的 exec 通道执行任何修复命令（尤其 `setenforce 1`
> 会把通道卡死），全部走 adb root。

**Step 7 补建 ashmem 节点（一般无需，兜底用）**

SakiSU 模块 insmod 时已在内核侧把 boot_id 精确恢复为原始 UUID，init 开机创建
的节点自然匹配，通常无需手动补建。仅当 app 仍闪退时兜底执行：

```
adb push scripts\fix_ashmem.sh /data/local/tmp/fix_ashmem.sh
adb shell sh /data/local/tmp/fix_ashmem.sh
```

**Step 8 修网络**

```
adb shell "setenforce 0; echo 0 > /proc/sys/kernel/modules_disabled; setenforce 1; load_policy /sys/fs/selinux/policy; echo rc=$?"
```

`rc=0` 后 `ping -c 2 www.baidu.com` 应 0% 丢包。

**Step 9 验证**

```
adb shell cat /sys/fs/selinux/enforce     REM = 1
adb shell id                              REM uid=0 context=u:r:ksu:s0
adb shell ping -c 2 www.baidu.com         REM 0% 丢包
REM app 抽检（QQ）：
adb shell "am force-stop com.tencent.mobileqq; am start com.tencent.mobileqq/.activity.SplashActivity"
adb shell "sleep 9; ps -A | grep mobileqq"    REM 主进程 + :MSF 存活
```

## 五、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 发枪后手机自动重启 | exploit 竞态失败（约 10% 概率） | 正常现象，重启后从 Step 0 重跑 |
| SakiSU 提示「未安装」 | 模块未加载 | 检查 Step 5 的 INSMOD_DONE rc=0 与 lsmod |
| SakiSU 进不了设置页 | 未授权 root | 先授权再进设置 |
| `adb root` 不生效 | 未授权或开关没开 | Manager 里授权 → 开 ADB root → 关了再开 → 重试 |
| app 闪退 | 极罕见：boot_id 残留兜底场景 | 跑 `sh /data/local/tmp/fix_ashmem.sh`（boot_id 漂移已由内核模块的 bootid 参数根治） |
| 能 ping IP 不能解析域名 | load_policy 没执行成功 | 重跑 Step 8 |
| `getenforce` 显示 Permissive | KSU 劫持了 getenforce | 以 `cat /sys/fs/selinux/enforce` 为准（=1 即 Enforcing） |
| 卡死 | — | 长按电源键强制重启，从 Step 0 重来 |

## 六、注意事项

1. **每次开机都要重跑**（BL 锁不可解，root 不持久化）；每次开机的 kallsyms
   与补丁产物**不可跨 boot 复用**。
2. **不要修改系统分区 / vendor_boot**。
3. 操作前备份重要数据；root 后银行类应用可能受影响，可用 SakiSU 的隐藏功能缓解。
4. 仅供学习研究，请遵守当地法律法规，风险自负。
