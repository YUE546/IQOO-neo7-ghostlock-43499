# 原理与移植笔记 — GhostLock for iQOO Neo7 (MT6983T)

> 本文是技术主文档：漏洞与利用链逐阶段解析、与上游 GhostLock 的完整差异、
> MT6983T 实测偏移值表、移植开发过程与版本链。操作步骤见
> [使用指南.md](使用指南.md)，概览见仓库根 [README](../README.md)。

## 1. 漏洞：CVE-2026-43499

MTK vendor 修改的 5.10 内核对 futex PI requeue 路径的清理函数
（`rt_mutex_remove_waiter`）引入了缺陷：`FUTEX_CMP_REQUEUE_PI` 在特定错误条件
（返回 EDEADLK，errno=35）下，本应按 `waiter::task` 清理"被代理线程"的状态，
却用了 `current`。结果是被代理线程的 `task->pi_blocked_on` 残留为指向**自己
内核栈**上已逻辑释放的 `rt_waiter` 的悬垂指针——栈内存实际未擦除（"ghost"），
且用户态可通过后续 syscall 的栈帧拷贝精确覆写 ghost 内容。

两个内核机制被借道：

- **walk**：对 waiter 线程调用 `sched_setattr` 触发
  `rt_mutex_adjust_prio_chain`，它完全信任 `pi_blocked_on`，把 ghost 当真
  waiter 解引用、走红黑树；
- **stamp**：把用户数据拷到与 ghost 重叠的内核栈帧（载体 syscall，见 §3.2）。

红黑树 `rb_erase` 在本内核的编译形态下，"右子空、左子非空"分支恰好编译成
`str word0,[word2]` —— word0/word2 均来自伪造 waiter ⇒ **每次 walk 一次
8 字节内核任意写**。

## 2. 完整利用链（r44 定版）

```
触发 EDEADLK 形成 ghost（errno=35，实测 100% 复现）
→ mcast stamp：setsockopt(TCP6, IPPROTO_IPV6, 44, gsr, 264)
   （gsr 260B 拷贝落点覆盖 ghost，waiter 全 10 词用户可控，实测 shift=21）
→ walk 消费假 waiter → rb_erase 8 字节内核任意写
→ HIJACK：ctl.data := &nf_loggers → 借 boot_id sysctl 读 16B 内核内存
→ KASLR：perf_event IP 采样 oracle（HW PMU，失败回退 SW cpu-clock）
   + KernelSnitch bruteforce（仅干净 boot）
→ OWNER：读 anchor mm->owner (mm+0x348) → anchor task
→ VERIFY：读 task->comm 校验 "ksanch0r"
→ CRED：*(task+0x780) := init_cred → anchor getuid()==0
→ SELinux：*(selinux_state+0) := 0 → Permissive（FLIP_PERMISSIVE=1 时）
→ KSU_LOADER=1：anchor 以 kernel 域 + 全部 caps（CapEff=0x1ffffffffff）执行
   rundir/ksu_loader.sh
   → 阶段1：kptr_restrict=0 + 拉 /proc/kallsyms → 写 KALLSYMS_DONE 标记
   → 电脑端：pull kallsyms → patch_vermagic → patch_shnabs → push ko
   → 阶段2：等 ksu_ready 信号 → insmod SakiSU.ko
→ KSU 接管 root（su → uid=0 context=u:r:ksu:s0）
→ 后处理：补建 /dev/ashmem<boot_id> 节点（修复 app 冷启动）
   + load_policy 重载（修复 DNS/网络）
→ Enforcing 下 QQ/Kimi 冷启动正常 + 网络正常
```

### 2.1 任意读写原语

HIJACK 把 `boot_id` ctl_table 项的 `data` 字段（`CTL_BOOTID_DATA_OFF`）改指
目标地址后，`cat /proc/sys/kernel/random/boot_id` 即可读回该地址处 16 字节；
按 UUID 格式 `echo` 写回即写入 16 字节（mode 需先改为 0666，exploit 自动处理）。
这条"sysctl 直读"路径比逐字节爆破稳定得多，是上游 GhostLock 的核心设计，本
移植完整继承。

### 2.2 栈载体：mcast TCP6（本移植的主要贡献点）

ghost 位置固定在 syscall 入口 SP 之下 S−0x290 处（pstore 三代实测一致，x28 低
12 位恒 0xb10）。载体 syscall 的内核栈帧里必须有一块**位置可预测、内容用户
可控**的拷贝落点，正好覆盖 ghost 的 10 个 word（`rt_mutex_waiter` 的
entry/task/lock/prio/deadline 等）。

**上游方案**：荣耀 5.10.168/209 用 `pselect` 的 3×fd_set 栈拷贝；
5.10.236 起 fd_set 窗口变化，改用 mcast `group_source_req`（264B）拷贝——
gsr word 23 对准 waiter word 0（`SLIDE_MCAST_SHIFT=23`），optname 默认 46，
ROUNDS=300、GAP_US=50 为编译期常量。

**本机情况**：

1. **pselect fd_set 在 MT6983T 结构性不可达**：fd_set 栈窗口与 ghost 位置差
   0x80；`nfds>320` 时 fd_set 落堆不落栈。约 14 个 boot 的系统实测（g1–g31
   系列）判死，r39 pselect 线终止。
2. **mcast TCP6 实测定标 shift=21**：静态反汇编逐帧求和（`__sys_setsockopt`
   0x80 / sock_common 0x40 / tcp 0x40 / ipv6 0x40 / do_ipv6 0x60+0x270，合计
   0x420）推出 gsr 基址 S−0x2c8 → shift=+7。但 m1 用 DIAG 模式发枪 panic，
   解码故障地址 far=0x000d0000000000e0 得到实测 shift=**21**——比静态推导多
   0x70，归因于 vendor syscall 包装层多出的一帧（MTK 定制，未深究，不影响
   利用）。教训：**MTK vendor 内核的静态帧深求和不可信，必须实测定标**。
3. **参数带**：GAP_US<300 会撞脏窗口竞态 panic，实测 ≥300 起占空比稳定；
   ROUNDS=10000 提供足够重试余量。三个参数（SHIFT/GAP_US/ROUNDS）在上游是
   编译期常量，本移植全部改为运行时环境变量（`slide.c`），方便逐 boot 调参。

optname 选 44（`MCAST_BLOCK_SOURCE_GROUP`）：5.10.233 上 44/46 共享同一拷贝
块（无荣耀 5.10.236 的深度分裂），44 与上游 5.10.236 家族一致。TCP6 socket
（AF_INET6/SOCK_STREAM 未连接）的分发链比 UDP6 深一帧但 word0 干净；UDP6
尾调直入 do_ipv6 虽浅一帧（shift=-1），会把 tree_pc 留给随机栈残留，首发
`rb_erase` 父路径即消费垃圾——r40 因此弃用。

### 2.3 KASLR 泄漏（r42 的 SW 回退）

- **perf IP 采样 oracle**（本移植新增）：`perf_event_open(PERF_TYPE_HARDWARE,
  HW_CPU_CYCLES)` 采样本线程内核态 IP，取最小值按 2MB 对齐得 text_base。
  uid 2000 可用（本内核 perf_event_paranoid=-1 的 boot）。
- **SW 回退**（r42）：部分 boot 上 HW PMU 无样本（厂商 perf-hal 占用计数器、
  热重启 PMU 状态残留），改用 `PERF_COUNT_SW_CPU_CLOCK` 采样，实测 samples
  662 即可命中（m5c）。
- **KernelSnitch**（承自上游）：futex hashbucket 侧信道 bruteforce。实测在
  **脏 boot**（有 parked walker 堆积）会连续失败，干净 boot 一发即中——所以
  发枪前必须确认 boot 干净（SELinux Enforcing + boot_id 为正常 UUID）。

### 2.4 CRED / SELinux

- `task->cred`（有效字段）@0x780（注意与 `real_cred`@0x778 区分），写入
  `init_cred`（0x2b010b0 + slide）一次命中即 `getuid()==0`。anchor 不能直接
  `commit_creds`（BUG_ON）。
- SELinux enforcing 字节 = `selinux_state+0`（偏移 0x2ec6900）。MT6983T 的
  `selinux_state` 布局有两种假设（disabled 占不占 byte0），通过 boot_id 16B
  读回 selinux_state 后实证为 H1（enforcing@+0），与荣耀一致（荣耀还有个
  +1 的 decoy 读点，本内核未发现）。
- `setenforce` 走 sysfs 被内核拦（-EINVAL），permissive 只能内存写。

## 3. 与上游 GhostLock 的完整差异

上游针对荣耀 80 GT（annap-AGT-AN00，高通平台，DRAM 基址 0x80000000，MagicOS
8/9，内核 5.10.168–5.10.236），本移植目标为 iQOO Neo7（联发科平台，DRAM 基址
0x40000000、内核物理加载 0x48000000，OriginOS Android 15，内核
5.10.233-android12-9）。除偏移表全新（见 §4）外，结构性差异：

| # | 维度 | 上游 | 本移植 | 原因 |
|---|---|---|---|---|
| 1 | 栈载体 | pselect fd_set →（5.10.236）mcast shift=23 | mcast TCP6 opt44 shift=21（env 可调） | pselect 窗口结构性不可达；MTK vendor 包装帧使实测 shift ≠ 静态推导 |
| 2 | 载体参数 | 编译期常量（ROUNDS=300/GAP_US=50） | env 变量（ROUNDS=10000/GAP_US≥300） | 逐 boot 调参需要；脏窗口竞态要求更大 GAP |
| 3 | KASLR | printk loggers 读回 + KernelSnitch | + perf IP 采样 oracle（HW/SW 双路） | 需要更快更稳的 slide 来源；HW PMU 部分 boot 失效 |
| 4 | 模块签名 | `CONFIG_MODULE_SIG_FORCE=y`，翻转 `sig_enforce` | 无签名强制（`is_module_sig_enforced()≡0`），跳过 | vivo 官核反汇编实证（P0 batch2） |
| 5 | vermagic | 无门禁 | **必须含 "vivo"** → patch_vermagic.py 重写 .modinfo | vivo 官核两套 ko 机制（GKI 期），vermagic 区分官核/通用驱动 |
| 6 | kallsyms | 厂商抹除符号名 → bind-mount 伪造 kallsyms | 符号名完整但 `kptr_restrict=2` → KSU_LOADER kernel 域窗口读取；未导出符号 SHN_ABS 注入 | 厂商对抗手段不同 |
| 7 | 未导出符号 | 上游方案不涉及 | SakiSU 引用 50 个未导出符号（含 do_syslog）→ patch_shnabs.py 把 kallsyms 运行时地址写入 .symtab（SHN_ABS） | modversions 官核不导出这些符号，insmod 解析 ENOENT（m19 实证） |
| 8 | KSU 移交 | ksud + magiskpolicy + ksu_rules | `KSU_LOADER=1` 两阶段脚本 + SakiSU LKM + SakiSU 管理器（com.sakisu.sakisu） | exploit 翻转后 exec 通道 CapEff=0（无 CAP_SYS_MODULE，m24/m25 实证）；SakiSU 才带 vivo vermagic 编译 |
| 9 | 厂商对抗 | hw_rscan（g_rscan_skip_flag） | vr.ko：不硬刚，速战速决 + `GL_ANCHOR_SURVIVE`（r43 新增，anchor 常驻供 KSU_LOADER/cmd watcher 使用） | vivo 反 root 模块在 vendorboot，BL 锁定无法移除 |
| 10 | boot_id | RESTORE 归还 | 放弃归还（mcast 路径连败），保留劫持 + 后处理修复 | RESTORE 在 m4 连败 4 次；劫持副作用可控（见 §5） |
| 11 | target 组织 | 按固件 target.h（18 个荣耀固件） | 新增 `targets/mt6983t-gl-5.10.233/`，荣耀 targets 保留 | 交叉移植参考 |
| 12 | boot_id 残留 | `init-bootid.patch` 让 .ko 内核侧恢复 | 同样移植进 SakiSU 构建（`bootid_ctl/bootid_buf` 模块参数） | 用户态 walk 恢复（FORCE_RESTORE）本机必硬重启，只能内核侧 |

继承不动的部分：boot_id ctl_table hijack 任意读写路由、anchor（ksanch0r）
校验链、fake waiter 布局与 rb_erase 写原语、kernelsnitch/ 目录、launcher/
Makefile/docker-build 构建系统、Apache-2.0 许可。

## 4. MT6983T 实测偏移值表

内核 `5.10.233-android12-9-gb877c11e0b75-dirty`，KIMAGE_TEXT_BASE =
0xffffffc008000000，运行时地址 = 基址 + slide + 偏移。取证方法标注：
[nm] = vmlinux-to-elf 符号表，[disasm] = 定向反汇编，[src] = 内核源码结构体
布局，[runtime] = 真机链路验证。完整机器可读版本见
`exploit/src/targets/mt6983t-gl-5.10.233/target.h`。

### task_struct

| 字段 | 偏移 | 验证 |
|---|---|---|
| usage | 0x40 | [disasm] get_task_struct ldxr |
| prio / normal_prio | 0x84 / 0x8c | [disasm] rt_mutex_setprio |
| sched_class | 0x98 | [disasm] str x8,[x20,#0x98] |
| real_cred / cred | 0x778 / **0x780** | [disasm] + [runtime] CRED 写 0x780 后 getuid()==0 |
| comm | **0x790** | [runtime] 读回 "ksanch0r" |
| pi_lock / pi_waiters / pi_top_task / pi_blocked_on | 0x86c / 0x880 / 0x890 / 0x898 | [disasm] adjust_prio_chain 交叉 |

### rt_mutex_waiter（5.10 classic 布局）

| 字段 | 偏移 |
|---|---|
| rb entry（parent_color） | 0x18 |

| 项 | 值 |

## 5. vivo 环境三个坑与修复（全部闭环）

### 5.1 第三方 app 冷启动失败 → 补建 ashmem 节点

- **现象**：Enforcing 下系统 app 正常，QQ/Kimi `am start` 后 3–5 秒进程消失；
  logcat 报 `Unable to open ashmem device /dev/ashmem<UUID> (No such file...)
  and /dev/ashmem (Permission denied)`；零 AVC。
- **根因**：exploit 劫持 boot_id（写 sysctl_bootid 缓冲 0x2ee5b75），但系统
  开机时创建的 `/dev/ashmem<boot_id>` 命名节点（major 10 minor 127，label
  `ashmem_libcutils_device`）仍用原始 boot_id → app（bionic libcutils 按当前
  boot_id 拼路径）ENOENT → fallback `/dev/ashmem`（label `ashmem_device`，
  untrusted_app 无 open）→ SharedMemory 构造失败 → Activity 崩溃。
- **决定性对照**：无 KSU + GhostLock + Enforcing 下 app 同样失败（m21）——
  推翻"KSU policy 丢规则"假设；原始 policy 与 KSU policy 的 app 规则经
  sesearch 全量对比完全一致。
- **修复（2026-10-01 终版：内核侧精确恢复）**：链路结束后 ctl.data 悬在已释放的
  direct-map 页上，其内容随内核内存复用持续变化 → boot_id 整个 boot 内不断漂移
  （实测 "Jit thread pool"、"binder:1085_8"、r00000 系列等字符串的 hex 形式）。
  一次性补建节点治标不治本，残留还会引发软重启后 PM 扫描窗口异常、框架重启卡死
  等问题。终版修复是把上游 GhostLock 的 `ksu/init-bootid.patch` 核心移植进
  SakiSU 构建：模块新增 `bootid_ctl`/`bootid_buf` 参数，insmod 时在内核侧把
  ctl.data **精确**写回 sysctl_bootid 真缓冲区（地址由 exploit 写入
  `rundir/ksu_runtime.env`，`ksu_loader.sh` 带参 insmod）。此后 boot_id 读回
  原始 UUID、与 init 开机创建的 `/dev/ashmem<UUID>` 节点精确匹配、不再漂移；
  软重启（框架重启）后残留消失，实测通过。**死路**：用户态
  `FORCE_RESTORE=1`（走 walk 的 restore 模式）在本机必硬重启——恢复只能走
  内核侧。

### 5.2 DNS 断网 → load_policy 重载

KSU 替换 policy 后 netd/resolver 内核状态不一致（只有 IPv6 DNS 无 IPv4 DNS，
ping IP 通、解析域名失败）。修复序列：

```sh
setenforce 0; echo 0 > /proc/sys/kernel/modules_disabled; setenforce 1
load_policy /sys/fs/selinux/policy
```

load_policy 返回 0 后 DNS 立即恢复。**只修网络，不修 app 冷启动**（m26 对照）。

### 5.3 exec 通道 caps=0 → KSU_LOADER 两阶段

exploit 翻转 cred 后，若直接在其 exec 通道（cmd watcher）里执行命令，进程
CapEff=0：不能 insmod、kallsyms 读到全 0 地址。但 exploit 内置的
`KSU_LOADER=1` 模式会让 rooted anchor 以 `u:r:kernel:s0` + 全部 caps
（CapEff=0x1ffffffffff）fork 执行 `rundir/ksu_loader.sh`——两阶段设计：

1. 阶段 1（自动）：`kptr_restrict=0` + `cat /proc/kallsyms` → 写
   KALLSYMS_DONE 标记；电脑端 pull 后跑补丁链；
2. 阶段 2（等信号）：循环等 `/data/local/tmp/ksu_ready` → `insmod`。

**切记**：绝不能用 exec 通道执行 `setenforce 1`——会触发 ksucmdwatch 僵尸
风暴（上百 `[r00000]` 僵尸进程）卡死通道，只能重启。所有后处理走 adb root。

## 6. SakiSU 模块构建要点

内核模块是 SakiSU（酷安社区基于 ReSukiSU 的 vivo 适配分支）`kernel/` 目录，
在 GKI 5.10 构建环境（内核源码树 + clang-14/LLVM=1）编译：

```sh
cd /path/to/gki            # 匹配内核系列的构建树
export PATH=/usr/lib/llvm-14/bin:$PATH
make ARCH=arm64 LLVM=1 LLVM_IAS=1 M=drivers/kernelsu -j1
# 前置：手动建 include/generated/compile.h（最小内容）；
#       确认 include/generated/flask.h symlink 有效
# 产物 drivers/kernelsu/kernelsu.ko → llvm-strip-14 → 364KB（sakisu_raw.ko）
```

产物经 `patch_vermagic.py`（vermagic 加 "vivo"）+ `patch_shnabs.py`（50 个
未导出符号 SHN_ABS 注入）后即可在官核 insmod。**跨 boot 不能复用补丁产物**：
KASLR 每次开机变化，SHN_ABS 地址必须用当次开机 kernel 域拉取的 kallsyms
重打。

本仓库随附的构建额外包含 boot_id 内核侧恢复（移植自上游
`ksu/init-bootid.patch`）：`kernel/core/init.c` 新增 `bootid_ctl`/`bootid_buf`
模块参数与 `restore_bootid()`，在 `kernelsu_init` 开头调用。insmod 由
`ksu_loader.sh` 带参执行，参数取自 exploit 写出的 `rundir/ksu_runtime.env`
（BOOTID_CTL_RT = ctl_table 表项地址，恢复写 ctl+8 = data 字段；BOOTID_BUF_RT
= sysctl_bootid 缓冲区地址）。注意 strip 必须用 `llvm-strip-14 -g`（保留
.symtab 供 SHN_ABS 注入），全量 strip 会把符号表删掉导致 patch_shnabs 无法
工作。

### 已验证死路（勿重试）

1. pselect fd_set 载体（窗口差 0x80，nfds>320 落堆）
2. 静态推导 shift=7 直接发枪（必 panic，far=残留垃圾）
3. mcast UDP6（word0 残留）
4. RESTORE 归还 boot_id（mcast 路径成功率极差）
5. exec 通道 insmod / 读 kallsyms（caps=0）
6. exec 通道执行 `setenforce 1`（ksucmdwatch 僵尸风暴卡死通道）
7. 跨 boot 复用 kallsyms / 补丁产物（KASLR 变化）
8. 用发枪时的 boot_id 补建 ashmem（KSU 加载后 boot_id 会再变）
9. KSU 加载前提前开 adb root（未授权时 Manager 不生效）
10. rmmod kernelsu（引用计数非 0，只能重启）
11. 修改系统分区 / vendor_boot repack（本项目硬约束，不在方案内）
12. `FORCE_RESTORE=1`（exploit 用户态 restore walk）：本机实测发枪后必硬重启
    （即源码注释所述 post-permissive restore hard-reset）——boot_id 恢复必须
    走内核侧（SakiSU 的 bootid 模块参数）

## 8. vr.ko（vivo 反 root 模块）应对

- 位于 vendorboot 分区 ramdisk，开机加载后隐藏于 /proc/modules（`/sys/module/vr`
  可见）；行为：遍历内核链表检测钩子改动、击杀 root 进程。
- BL 锁定 + 本项目硬约束（不动系统分区/vendor_boot）下无法移除。
- 实测应对：速战速决——KSU_LOADER 两阶段在发枪后 60–90s 内完成 insmod，
  远在 vr 检测窗口生效前；`GL_ANCHOR_SURVIVE=1` 保持 anchor 存活（实测
  54min+ 无击杀）。截至目前 vr.ko 未对链路造成实际影响。
